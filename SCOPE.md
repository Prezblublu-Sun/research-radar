# Research Radar — Scope

This document defines what Research Radar does and explicitly does NOT do.
It exists so that future expansion requests (including those generated by LLMs)
can be evaluated against a fixed boundary, not against vague aspirations.

This boundary is informed by 2026-05-12 audit experience: an LLM-generated
suggestion document proposed expanding Radar into RAG / Docling territory,
which would overlap with lit-system and dilute Radar's purpose.

---

## What Research Radar IS

Research Radar is a **literature discovery layer**: a daily-running, low-cost
system that scans new academic publications, scores their relevance to a
fixed set of research directions, and delivers a curated digest.

Concretely, it:
- Pulls new papers from arXiv, OpenAlex, PubMed (and potentially journal RSS later)
- Deduplicates by DOI
- Routes papers to research directions using keyword rules
- Scores each paper with an LLM (priority + bilingual summary + key terms)
- Renders a daily/weekly HTML digest at GitHub Pages
- Syncs Medium+ papers to Zotero collections, one per direction
- Records every run with manifest + CHANGELOG (version governance)

Properties:
- Runs autonomously on GitHub Actions (no local machine required)
- ~¥0.5/day operating cost (DeepSeek LLM calls)
- 4-layer data persistence (Pages / main / Releases / Zotero)
- Versioned (config snapshots, prompt versions, model snapshots, package versions)

---

## What Research Radar is NOT

These are explicitly out of scope and belong to other systems (primarily lit-system):

### Full-text processing
- PDF download (except via Zotero client by the user manually)
- PDF parsing (Docling, GROBID, pypdf, etc.)
- OCR
- Equation / figure / table extraction

### Knowledge construction
- Chunking
- Embedding (any vector model)
- Vector store (Chroma, Qdrant, FAISS, etc.)
- Retrieval-Augmented Generation (RAG)
- Knowledge graph construction
- Citation graph analysis
- Author / institution disambiguation beyond what OpenAlex provides

### Deep semantic operations
- Multi-paper synthesis beyond the weekly LLM meta-summary
- Cross-paper comparison
- Literature review generation
- Research gap identification
- Hypothesis generation
- Methodology recommendation

### Personalization / interaction
- User feedback loops (thumbs up/down on papers)
- Active learning of preferences
- Personalized re-ranking
- Conversational interface
- Chat-with-papers

### Acquisition / curation operations beyond fetch+filter
- Manual ingestion of user-provided PDFs
- Curation interface (web UI for marking papers)
- Annotation tools
- Reading-progress tracking

## The Radar to lit-system contract

Research Radar is the upstream feeder to lit-system.

Research Radar discovers new papers, LLM-scores their priority, and syncs
Medium+ papers to Zotero. It renders a daily digest and logs run metadata.

lit-system receives those candidates, deep-parses them with Docling, builds
a RAG knowledge base from the parsed content, and answers research questions.

Interface (planned, W2.3): A simple JSONL export at
data/exports/candidates.jsonl that lit-system reads to ingest High/Medium
papers. No tight coupling — file-based handoff.

The contract: Radar guarantees fresh, relevance-filtered candidates with
stable identifiers (DOI). lit-system guarantees not to push deep-parsing
responsibilities back upstream.

## How to evaluate future feature requests

When considering adding a new feature, ask in order:

1. Does it expand the "what Radar IS" list? → Probably accept, but check item 2.
2. Does it touch any "what Radar is NOT" item? → Reject. That is lit-system's job.
3. Does the proposer assume Radar has data it does not have (e.g., full text, embeddings)? → Reject.
4. Can the deliverable from one Radar run already produce it? → Probably not worth adding to Radar; do it as a downstream consumer.
5. Would this make Radar more brittle, slower, or more expensive without proportional value? → Reject.

A feature passes only if it strengthens the discovery / scoring / digest /
sync loop, without leaking into deep-parsing territory.

## Why this scope, and not bigger?

A larger Radar would:
- Compete with lit-system instead of feeding it
- Increase maintenance cost beyond ¥0.5/day
- Introduce dependencies (PDF servers, vector DBs, queue systems)
- Make the daily run unreliable (timeout risk)
- Become a second copy of partial functionality

By staying narrow, Radar can:
- Run in 2-3 minutes daily on free GitHub Actions
- Be maintained by one person in less than 1 hour/month
- Be replaced or rewritten without losing the value chain
- Provide a clean, file-based interface to whatever comes downstream

This narrow scope is the design.
